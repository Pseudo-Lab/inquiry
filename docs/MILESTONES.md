# Inquiry 마일스톤

> 관련 문서: [`PRODUCT-CONCEPT.md`](./PRODUCT-CONCEPT.md) · [`REVIEW.md`](./REVIEW.md)
> 작성일: 2026-08-28
> 상태: 초안 (개발 전)

## 원칙

- **게이트 기반.** 각 마일스톤은 명시적 exit 기준을 통과해야 다음으로 넘어간다. 날짜보다 "무엇을 검증했는가"가 기준.
- **가장 싼 검증부터.** 실패했을 때 손실이 큰 가정을 먼저, 싸게 확인한다.
- **결정이 코드를 막는다.** M0의 블로킹 결정이 안 되면 M2 이후 코드를 못 짠다 (REVIEW §1 참조).
- 순번은 의존 순서다. `M1a`·`M1b`처럼 병렬 가능한 것은 표시했다.
- **진행 형태: 혼자(solo).** 병렬 표시(M1a·M1b)는 논리적 독립성일 뿐, 실제로는 순차 진행이 현실적. M4(Team Mode)는 **우선순위 하향** — M2·M3 완성이 우선.
- **기간은 상대 소요(solo 기준 대략치).** 캘린더 날짜 아님. 리소스/집중도에 따라 유동.

```text
M0 결정  ─▶  M1a Framing ─┐
                          ├─▶ M2 코어 결합 ─▶ M3 OSS MVP ─▶ (M4 Team) ─▶ M5 확장
             M1b TUI ─────┘
누적(solo): ~1주   ~2주        ~5~6주        ~12~14주      후순위        미정
```

## M0 — 블로킹 결정 (개발 전 확정)

> 예상 소요: **~1주** (조사·결정 중심, 코드 없음)

첫 코드보다 먼저. 산출물은 코드가 아니라 **결정 문서**(`docs/decisions/` ADR — 아래 6건 생성됨).

| # | 결정 항목 | 권장안 (REVIEW) | 출처 |
|---|---|---|---|
| D1 | canonical 저장 형식 | 이벤트 로그 원본 + Markdown projection + 파생 인덱스 | REVIEW 부록 A |
| D2 | 그래프 모델 | MVP는 DAG-only | REVIEW 1-② |
| D3 | confidence 데이터 모델 + provenance 규격 | 범위+출처, 업데이트/decay 규칙 명시 | REVIEW 1-③, §21.10 |
| D4 | agent adapter 계약 | 스트리밍·tool call·비용 회계·heartbeat 프로토콜 | REVIEW 1-④ |
| D5 | 가설 상태 머신 | 허용 전이 표 + 불변식 확정 | REVIEW 부록 B |
| D6 | 비용 모델 | inquiry별 spend cap·예산 UI 기본 정책 | REVIEW 3-비용 |

각 결정의 초안 ADR: [`docs/decisions/`](./decisions/) (D1~D6, 현재 *Proposed* 상태).

**Exit 기준:** D1~D6 ADR이 *Accepted*로 확정되고, 서로 모순 없음(특히 D1↔§4.7 문구 정합).

## M1a — Framing Session 검증 (개발 시작점)

> 예상 소요: **~1주** · 스택: **Python** (LLM SDK 연동)
> 상태: **실행 검증 작업 마감, UX 잔여 항목 명시** — 자동 5종 15항목과 실제 답변 재개 검증 통과. 최초 사용 UX의 최종 확인은 미실시이며 무조건 Exit 통과는 아님. [마감 보고서](reports/m1a-closeout.md).

- **목적:** 막연한 입력 → 3~5문항 → 탐구 프레임 생성의 프롬프트 품질만 검증. 그래프·TUI·저장 전부 없음.
- **산출물:** 단일 스크립트(입력 → Q&A → 프레임 텍스트). → `prototypes/m1a-framing/framing.py` (모델: `gpt-6-astra`, OpenAI API; ADR-D4 2026-09-10 변경).
- **범위:** 원문 §7 (기본 3문항 + 적응형 후속), 5종 입력 테스트(연구/제품/정책/창작/사고실험).
- **Exit 기준 (REVIEW 부록 C-0a):**
  - 질문이 유도적이지 않고 3~5문항 안에 프레임이 잡힘
  - 5종 모두 "중심 질문 + 판단 기준 + 범위" 타당
  - 초기 가설 후보가 서로 성격이 다름(중복 아님)
- **실패 시:** 여기서 멈춘다. 제품 첫인상 급소.

## M1b — 정적 TUI 레이아웃 검증 (M1a와 논리적 병렬, solo는 순차)

> 예상 소요: **~1주** · 스택: **Python** (Textual/Rich 후보)

> 상태: **디자인 선택 완료 — 박스형 세로 Git-log**. 사용자 승인으로 다른 시안은 보관했다. 현재 선택안의 연속·합류·종료 예시와 80/100/120열 검증 완료. 기존 전체 노드 매트릭스의 선택안 적용은 남아 있다. [실행법](../prototypes/m1b-layout/README.md) · [선택안 및 평가](reports/m1b-branch-scenarios.md). M1a와 독립 진행 가능(C-0b).

- **목적:** terminal-first 전제(§9) 자체의 검증. 에이전트·상태변경 없이 하드코딩 가짜 그래프만.
- **산출물:** 박스·고정 열이 있는 세로 Git-log TUI 목업. 사용자 요청으로 컬러와 흑백 출력을 지원하며 그래프·ID·가설·상태를 같은 박스에 표시한다. 클릭/키보드 상세 탐색은 MVP 이후 계획을 유지한다.
- **테스트 매트릭스:** 폭 80·120·160 × 노드 10·30·100.
- **Exit 기준 (REVIEW 부록 C-0b):**
  - "위=지지, 아래=반박, 중심선=계보"가 설명 없이 읽힘
  - 100노드에서 정보 과밀로 무너지지 않음(또는 compact 폴백 자연스러움)
  - 색 없이 기호+텍스트만으로 상태 구분 가능(접근성)
- **실패 시:** terminal-first 재검토(웹 뷰어 조기 도입 등).

## M2 — 코어 결합 (원문 Phase 0 완성)

> 예상 소요: **~3~4주**

- **전제:** M0 확정 + M1a·M1b 통과. D1(이벤트 로그)·D5(상태 머신)가 여기서 처음 코드화.
- **범위:** `fork`·`deepen`·`challenge`·`synthesize`·`close` 5연산 + 상태 전이 + 노드 상세 + 체크박스 Actions + Weekly preview + Markdown export. 단일 사용자·로컬.
- **노드 상세 범위:** MVP 탐구 흐름에 필요한 기본 정보 조회까지만 포함한다. 지도에서 마우스 클릭·키보드로 노드를 선택해 상세를 탐색하는 UX와 브랜치 전체 요약은 아래 **MVP 이후 상세 탐색 계획**에서 다시 구체화한다.
- **Exit 기준:** 원문 §18 시나리오 1~10을 처음부터 끝까지 완주.
- **명시적 제외:** 컬러·애니메이션, 다중 에이전트, saturation/dedup, 실시간 동기화, presence/claim/lease.

---

## M3 — Open-source MVP (원문 Phase 1)

> 예상 소요: **~6~8주**

- **범위:** 컬러 상태 표현, 저속 활동 애니메이션(진짜 heartbeat 기반, §10), 다중 에이전트 actor, evidence·confidence 출처 관리(D3), 사고 포화·중복 감지(§8), `NOW/NEXT/LATER`, Weekly·research note·decision record 템플릿, Git 버전관리, `--no-color`/`--no-animation`/ASCII fallback.
- **주의 (REVIEW):** saturation/dedup(§8)은 연구 난이도. **단순 휴리스틱으로 시작**하고 임베딩 기반은 점진 도입. 여기서 완벽을 노리지 말 것.
- **Exit 기준:** 외부 사용자가 설치→Framing→탐구→Weekly export를 문서 없이 완주. OSS 공개 가능 수준.

---

## MVP 이후 상세 탐색 계획 — M3 완료 후 재검토

> 상태: **백로그 / 계획 구체화 대기** · 사용자 요청으로 MVP 이후에 논의. M3 완료 조건에는 추가하지 않는다. M4 Team Mode와 독립적으로 검토한다.

- [ ] **노드 상세 탐색:** 지도에서 마우스 클릭 또는 키보드로 노드를 선택해 상세 정보를 보는 흐름을 설계한다.
- [ ] **상세 정보 범위:** 현재 상태, 가설의 주장, 지지·반박 근거, 연결된 가설 중 무엇을 보여줄지 정한다.
- [ ] **브랜치 요약:** 개별 노드 상세와 구분하여 브랜치 전체의 진행 상태·주요 쟁점을 요약할 필요성과 표현 방식을 검토한다.
- [ ] **조작과 접근성:** 클릭·키보드 간 기능 동등성, 포커스 이동, 상세 열기·닫기, 지도 복귀 및 좁은 화면 배치를 구체화한다.
- [ ] **구현 계획 확정:** MVP 사용 경험을 바탕으로 우선순위, 수용 기준, 구현 마일스톤을 정한다.

**이번에 확정한 것:** MVP 완료 후 이 계획을 다시 다룬다는 일정과 백로그 등록. 구체적인 키 바인딩·패널 구성·브랜치 집계 규칙 및 구현 시점은 아직 확정하지 않는다.

## M4 — Team Mode (원문 Phase 2) · 후순위

> 예상 소요: 미정 (solo 진행이라 **우선순위 하향**) — M2·M3가 안정된 뒤 필요성 재판단

- **범위:** 실시간 presence, claim/lease, heartbeat·stale worker 감지, 담당자/실행자/reviewer 분리, 팀 활동 피드, 충돌→대안 브랜치 보존, 팀 Weekly·shared Actions.
- **solo 참고:** 혼자 진행이므로 이 단계는 당장 필요 없음. 다만 D1(이벤트 로그)을 M0에서 제대로 정해두면 나중에 팀 모드를 붙일 때 재작업이 적다 — **지금은 만들지 않되, 설계가 이를 막지 않도록만** 한다.
- **선결 (REVIEW):** **정체성/인증** 설계(§11 전제인데 원문 누락). 팀 서버 self-host 여부 확정(로컬 우선 약속과의 정합).
- **주의:** 그래프 병합·충돌 복구는 최상위 난이도(CRDT급). D1의 이벤트 로그가 여기서 값을 함.
- **Exit 기준:** 2명 이상 + 다중 에이전트가 충돌 없이 동시 탐구, 충돌 시 브랜치 보존 동작.

---

## M5 — 확장 (원문 Phase 3)

- **범위:** 웹 그래프 뷰어, 고급 시뮬레이션 플러그인, 문헌·데이터·인터뷰 connector, 외부 게시 연동, 조직별 템플릿·정책, 그래프 간 knowledge link, (선택) 그래프 순환 허용.
- **Exit 기준:** 미정 — M4 이후 사용자 피드백으로 재정의.

## 미결 (마일스톤 관점)

- 상대 기간은 solo 대략치. **실제 캘린더 일정**은 착수 시점에 별도 부여.
- 최종 프로젝트 이름·CLI command 확정 시점(§21.1) → 늦어도 M3(OSS 공개) 전.
- 구현 언어는 **Python 확정**. TUI 라이브러리(Textual vs Rich 등) 최종 선택은 M1b에서 검증 후 M2 착수 전 확정.
- M4(Team Mode)는 solo라 후순위 — M3 이후 실제 협업 수요가 생기면 재평가.
