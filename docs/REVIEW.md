# Inquiry 콘셉트 문서 리뷰

> 대상 문서: [`PRODUCT-CONCEPT.md`](./PRODUCT-CONCEPT.md)
> 리뷰 관점: **결정해야 하는 부분 / 어려운 부분 / 위험한 부분**
> 작성일: 2026-08-28
> 리뷰 상태: 초안 (개발 전 검토)

## 총평

야심이 매우 크다. 이 한 제품이 사실상 **그래프 DB + 에이전트 오케스트레이터 + 터미널 TUI 프레임워크 + 실시간 협업 서버 + 문서 생성기**를 동시에 하려고 한다. 콘셉트의 일관성과 철학은 훌륭하지만, **"쉬워 보이게 써 놓았지만 실제로는 각각이 독립 연구과제인 부분"** 이 여러 곳에 숨어 있다.

원문에 이미 §20(위험)·§21(미결정)이 잘 정리돼 있으므로, 이 리뷰는 **거기서 빠졌거나 과소평가된 것** 그리고 **서로 충돌하는 결정들** 위주로 정리한다.

## 1. 반드시 먼저 결정해야 하는 부분 (다른 모든 걸 막는 결정들)

### ① 저장 형식 — 최상위 병목 (§16, §21.2)

문서는 세 옵션을 병렬로 나열했지만, 이건 "나중에 프로토타입에서" 미룰 수 있는 게 아니라 **거의 모든 하위 설계를 결정하는 뿌리**다. 그리고 여기엔 **정면충돌하는 두 요구**가 있다.

- §4.7 "로컬 우선, 개방형 Markdown 포맷" (이식성)
- §11 / §17 Phase 2 "실시간 팀 동기화 + 충돌 복구" (동시성)

이 둘은 반대 방향으로 당긴다. Markdown 파일을 canonical로 두면 실시간 병합·충돌 복구가 지옥이 되고, 이벤트 로그(JSONL)를 canonical로 두면 동기화는 깔끔하지만 **"진짜 원본은 사람이 못 읽는 이벤트 로그"가 되어 §4.7의 약속이 사실상 약해진다.**

> **권장**: 이벤트 로그(append-only)를 canonical, Markdown은 projection, import는 사람 승인 round-trip. 대신 §4.7 문구를 "원본은 개방형 이벤트 로그 + 언제든 Markdown export 가능"으로 정직하게 조정. 이 결정을 안 하면 Phase 0 코드도 못 짠다.

### ② 그래프 모델: DAG인가, 순환 허용인가 (§6.2, §21.3)

"DAG 또는 제한적 순환"으로 열어뒀는데, 순환을 허용하는 순간 아래가 전부 훨씬 어려워진다.

- staleness / drift 전파 (§12)
- "중심선과의 거리 = 개념적 차이" 시각 지표 (§9)
- synthesis 계보 추적

> **권장**: MVP는 **DAG-only**로 못 박기. 순환은 Phase 3 이후.

### ③ Confidence 데이터 모델 (§6.4, §21.4)

§6.4가 스칼라(`plausibility: 0.72`)와 범위(`range: [0.50, 0.80]`)를 **동시에** 쓰는데, 정작 "누가·언제·어떻게 업데이트하는가"가 없다. 에이전트 추정치가 시간이 지나면 decay하는가? 새 evidence가 붙으면 자동 재계산인가? 이건 §20 "가짜 정밀도" 위험과 직결되므로 **모델부터 못 박아야** 한다.

### ④ Agent adapter 계약 (§16, §21.5)

"특정 모델에 종속되지 않는 인터페이스"는 말은 쉽지만, 실제 계약(스트리밍 / tool call / **비용·토큰 회계** / heartbeat 프로토콜)이 정의돼야 §10의 "진짜 heartbeat 있는 것만 애니메이션"과 §11의 presence가 성립한다.

## 2. 기술적으로 어려운 부분 (문서가 난이도를 과소평가한 곳)

| 기능 | 왜 어려운가 |
|---|---|
| **터미널 그래프 레이아웃** (§9) | 80/120/160 컬럼 × 10/30/100 노드에서 "위=지지, 아래=반박, 중심선 계보"를 읽히게 유지하는 2D ASCII 그래프 레이아웃은 사실상 미해결 난제. `git log --graph`보다 훨씬 어렵다. **이 제품의 가장 큰 UX 베팅인데 "프로토타입에서"로 미뤄져 있다.** |
| **사고 포화 감지** (§8) | 의미 중복도·novelty·confidence 변화로 에이전트 루프를 감지 — 임베딩 + 휴리스틱이 필요한 **연구 과제**. 과하면 탐색을 죽이고, 못 잡으면 토큰만 태운다. |
| **Framing Session** (§7) | 연구/제품/정책/창작/사고실험 입력 모두에서 유도 질문 없이 3~5문항으로 프레임을 잡는 것 — 견고하게 만들기 매우 어려운 프롬프트 엔지니어링. **첫인상 순간**이라 여기서 실패하면 이탈. |
| **실시간 팀 동기화 + 충돌→대안 브랜치 보존** (§11, Phase 2) | 그래프 위 병합 시맨틱스는 CRDT급 분산 시스템 난이도. "충돌을 브랜치로 보존"은 개념적으로 우아하지만 구현 난이도 최상위. |
| **drift 감지** (§12 drifting) | "하위 결과와 상위 평가 불일치"를 잡으려면 의미 관계 이해가 필요. 단순 날짜 비교로는 불가능. |
| **Markdown round-trip** (§14, §21.9) | 사람이 편집한 산문을 그래프 노드로 되돌리는 diff — 퍼지 매칭 문제. |

## 3. 위험한 부분 (§20 외에 추가로 보이는 것)

### 스코프 위험 — Phase 0가 너무 큼 (§17)

"UX 프로토타입"이라면서 Framing + 그래프 5연산 + TUI + Actions + Weekly + Markdown export를 한 번에 묶었다. 이건 프로토타입이 아니라 이미 작은 완제품이다. → **Phase 0을 더 쪼개야** 한다 (아래 5장 참조).

### 청중과 인터페이스의 모순

타깃은 **연구자·창업자·초기 제품팀**(§5)인데, 인터페이스는 **터미널 상주 TUI**(§9). 이 청중의 상당수는 터미널 네이티브가 아니다. 강한 의견(terminal-first)이 오히려 시장을 좁힌다. "누구를 위한 도구인가"를 다시 못 박거나, 웹 뷰어(Phase 3)를 앞당기는 걸 고려해야 한다.

### 비용 폭주 위험 (문서에 거의 없음)

여러 에이전트가 fork/deepen/challenge를 돌리면 토큰 비용이 폭발한다. §20이 "깊이·시간·비용 제한"을 한 줄 언급하지만, **비용 모델·예산 UI·inquiry별 spend cap이 전혀 설계돼 있지 않다.** 에이전트 중심 도구에서 이건 신뢰·운영상 실질 위험.

### 닭-달걀 품질 위험 (핵심 가치의 급소)

제품 가치는 **두 베팅이 동시에** 성립해야 한다: (a) 에이전트가 쓸 만한 가설·반론을 낸다, (b) 그래프/TUI가 과정을 읽히게 만든다. 그런데 (a)가 평범하면 그래프가 슬롭으로 가득 차고, 그러면 dedup/saturation 기계(§8)가 **초반부터 load-bearing**이 되는데 — 그 기계 자체가 어려운 부분이다. 악순환.

### "human owner" 거버넌스의 양날 (§4.4, §11)

좋은 원칙이지만 friction을 만든다. 에이전트 행동마다 승인 경계가 필요하면 관료적으로 느껴지고, 너무 느슨하면 비용·범위가 새어나간다. **승인 경계의 기본선이 미정의.**

### 정체성 / 인증 부재

presence·claim·lease(§11)는 사용자 식별을 전제하는데, 로컬 우선 OSS 도구에서 **인증을 어떻게 하는지 문서에 전혀 없다.** Phase 2 팀 서버의 self-host 여부와 함께 "로컬 우선" 약속과 충돌할 수 있다.

## 4. 문서 내부의 빈틈·불일치

- **§16 저장 결정 ↔ §4.7 약속** 이 서로 긴장 (1-① 참조).
- **§6.5 상태 전이도**가 ASCII로 애매하다. 어느 상태에서 `synthesized` / `human-closed`로 갈 수 있는지 불명확 → **명시적 상태 머신(허용 전이 표)으로 형식화** 필요.
- **§8 확장 연산의 "언제 노출할지"** 문맥 감지 로직 자체가 또 하나의 AI 기능인데 난이도가 언급 안 됨.
- **Evidence provenance / 인용 규격**(§21.10)이 미정인데, 이건 "가짜 정밀도 방지" 철학의 load-bearing 요소라 우선순위가 높아야 함.

## 5. 권장 우선순위 (무엇을 먼저 결정 / 검증할지)

### 개발 전 반드시 확정 (블로킹)

1. 저장 canonical = **이벤트 로그**, Markdown = projection (1-①)
2. 그래프 = **DAG-only** for MVP (1-②)
3. Confidence 데이터 모델 + provenance 규격 (1-③, §21.10)
4. Agent adapter 계약 + **비용 회계·예산 cap** (1-④, 3-비용)

### Phase 0을 아래 순서로 쪼개기 (각각 독립 검증)

- **0a. Framing Session만** — 그래프도 TUI도 없이, 5종 입력으로 프롬프트 품질만 검증 (§22-B). 가장 싸고, 실패 시 제품 전체가 흔들리는 급소.
- **0b. 정적 흑백 TUI 레이아웃만** — 가짜 데이터로 80/120/160 × 10/30/100 노드 가독성 검증 (§22-A). 여기서 안 읽히면 terminal-first 전제를 재검토.
- **0c.** 그 다음에 비로소 그래프 연산 + 상태 + export 결합.

즉, 원문 §22의 "권장 검증 3종"을 **Phase 0보다 앞에, 순차로** 두는 게 맞다. 지금은 그게 병렬/사후로 읽힌다.

## 부록 A. 저장 형식 3안 트레이드오프 + 최종 추천

원문 §16이 나열한 세 가지 canonical source 후보를 실제 요구사항 축으로 비교한다.

### A.1 세 안

- **안 1 — 이벤트 로그 원본**: append-only 이벤트 로그(JSONL)가 진실, Markdown은 projection으로 생성.
- **안 2 — Markdown 원본**: 엔티티별 Markdown 파일이 진실, 이벤트 로그는 감사 기록으로만.
- **안 3 — 로컬 DB 원본**: SQLite 등 로컬 DB가 진실, Markdown·이벤트 로그를 둘 다 export.

### A.2 비교표

평가: ◎ 강함 / ○ 보통 / △ 약함

| 요구 축 | 안 1 이벤트 로그 | 안 2 Markdown | 안 3 로컬 DB |
|---|---|---|---|
| 이식성 · SaaS 비잠금 (§4.7) | ○ (원본이 사람 비친화) | ◎ | △ (DB는 불투명) |
| 사람이 직접 파일 편집 | △ | ◎ | △ |
| 실시간 팀 동기화 (§11) | ◎ (이벤트 병합 자연스러움) | △ (파일 병합 충돌) | ○ (서버 필요) |
| 충돌 복구 → 대안 브랜치 보존 | ◎ | △ | ○ |
| 감사 · 재현 · 시간여행 (§16 event store) | ◎ | △ | ○ |
| 그래프 쿼리 · 상태 계산 성능 | △ (재생 필요) | △ | ◎ |
| Git 친화 버전관리 (§17 Phase 1) | ○ (append-only diff 깔끔) | ◎ | △ (바이너리) |
| 구현 복잡도 (낮을수록 좋음) | ○ | ◎ (초기) / △ (동기화 붙으면 급등) | △ |

### A.3 판단

핵심 긴장은 **이식성(안 2가 이김) vs 실시간 동기화·충돌 복구(안 1이 이김)**. 그리고 원문이 내세운 차별점(§4.5 실패한 아이디어 보존, §11 충돌→브랜치 보존, §16 "누가·언제·무엇을" 감사)은 **전부 이벤트 로그가 있어야 성립**한다. 즉 이벤트 로그는 어느 안을 골라도 사실상 필수다.

> **최종 추천: 안 1 (이벤트 로그 canonical) + Markdown projection + 파생 인덱스.**
>
> - **원본**: `.inquiry/events.jsonl` (append-only). 모든 상태·그래프는 이벤트 재생으로 도출.
> - **읽기 성능**: 재생 결과를 로컬 캐시(안 3의 DB를 *파생 인덱스*로만 사용, 언제든 재생성 가능 → 진실 아님).
> - **이식성**: `outputs/`와 엔티티 Markdown은 projection으로 항상 export (안 2의 장점 흡수). 사람 편집은 import round-trip으로 사람 승인 후 이벤트화(§14, §21.9).
> - **정직한 문구 조정**: §4.7을 "원본은 개방형 이벤트 로그(JSONL) + 언제든 Markdown export"로 수정. "Markdown이 원본"이라는 인상을 주지 않는다.
>
> 이렇게 하면 세 안의 강점(동기화·감사 / 이식성 / 쿼리 성능)을 각각 원본·projection·파생인덱스 레이어로 분리해 얻는다. MVP(Phase 0)에서는 파생 DB 없이 메모리 재생만으로 충분하다.

## 부록 B. §6.5 상태 머신 형식화

원문의 ASCII 다이어그램은 어느 전이가 허용되는지 애매하다. 아래처럼 **허용 전이 표**로 못 박기를 권장한다.

### B.1 상태 정의 (원문 §6.5 재확인)

`suggested` · `exploring` · `supported` · `contested` · `suspended` · `refuted` · `synthesized` · `human-closed`

이 중 **터미널 상태**(더 이상 자동 전이 없음): `synthesized`, `human-closed`.
`refuted`·`suspended`는 준-터미널 — 새 근거로 재개 가능.

### B.2 허용 전이 표

| From \ 트리거 | 전이 대상 | 트리거 | 주체 |
|---|---|---|---|
| `suggested` | `exploring` | 사람이 승인/탐색 시작 | human |
| `suggested` | `human-closed` | 사람이 채택 안 함 | human |
| `exploring` | `supported` | 지지 근거 우세 | agent 제안 → 자동/사람 |
| `exploring` | `contested` | 유의미한 상반 근거 등장 | agent/human |
| `exploring` | `suspended` | 판단 보류 결정 | human |
| `exploring` | `refuted` | 반박 근거 우세 | agent 제안 → 사람 확정 |
| `supported` | `contested` | 새 반례 등장 | agent/human |
| `supported` | `synthesized` | 상위 가설로 통합 | human (synthesize) |
| `supported` | `human-closed` | 사람이 명시 종료 | human |
| `contested` | `exploring` | 논쟁 해소 위해 재탐색 | human/agent |
| `contested` | `supported` | 반례 해소, 지지 회복 | agent → 사람 |
| `contested` | `refuted` | 반박 확정 | human |
| `contested` | `synthesized` | 통합으로 논쟁 흡수 | human |
| `suspended` | `exploring` | 재개(reopen) | human |
| `refuted` | `exploring` | 새 조건·근거로 reopen (§8 reopen) | human |
| `synthesized` | — | (터미널) | — |
| `human-closed` | `exploring` | 명시적 reopen (§21.11 조건 필요) | human |

### B.3 불변식 (invariant)

- 터미널/준-터미널 → 활성 상태로의 전이는 **반드시 human 주체**. 에이전트는 제안만, 확정은 사람(§4.4).
- `synthesized`로 갈 때는 통합 대상(부모) 가설 ID를 이벤트에 기록(계보 보존, §6.3).
- `refuted`·`human-closed` 진입 시 **종료 이유 + 당시 근거 스냅샷 + 재개 조건**을 필수 기록(§4.5).
- 모든 전이는 이벤트 로그에 `{from, to, trigger, actor, at, reason?}`로 append(부록 A와 정합).

### B.4 열린 질문

- `supported` ↔ `contested` 자동 왕복이 잦으면 flapping. confidence 히스테리시스(임계 밴드)로 완충할지 결정 필요.
- `human-closed` reopen 조건(§21.11)을 상태 머신 가드로 강제할지, 정책 문서로만 둘지.

## 부록 C. Phase 0 재분할 상세 계획

원문 Phase 0는 사실상 작은 완제품이다. **한 번에 검증하려다 무엇이 실패했는지 못 가리는** 구조라, 아래처럼 3개의 독립 검증 단계로 쪼갠다. 각 단계는 **다음 단계 진입 전에 통과/실패를 판정**한다.

### 0a. Framing Session 단독 검증

- **목적**: 막연한 입력 → 3~5문항 → 탐구 프레임 생성의 프롬프트 품질만 검증. **그래프·TUI·저장 전부 없음.**
- **산출물**: 단일 스크립트(입력 → Q&A → 프레임 텍스트 출력). 결과는 그냥 stdout/파일.
- **입력 5종 테스트**(§22-B): 연구 질문 / 제품 아이디어 / 정책 결정 / 창작 아이디어 / 순수 사고실험.
- **성공 기준**:
  - 질문이 유도적이지 않고, 3~5문항 안에 프레임이 잡힌다.
  - 5종 모두에서 "중심 질문 + 판단 기준 + 범위"가 사람이 보기에 타당.
  - 초기 가설 후보가 서로 성격이 다르게(중복 아님) 나온다.
- **실패 시**: 여기서 멈춘다. 제품 첫인상의 급소라 여기가 안 되면 나머지는 무의미.

### 0b. 정적 TUI 레이아웃 단독 검증

- **목적**: terminal-first 전제(§9) 자체의 검증. **에이전트·상태변경 없음, 하드코딩된 가짜 그래프만.**
- **산출물**: 정적 흑백 TUI 렌더러. 상단 상태줄 / 중앙 Possibility Map / 하단 Actions 목업.
- **테스트 매트릭스**(§22-A): 폭 80·120·160 컬럼 × 노드 10·30·100개.
- **성공 기준**:
  - "위=지지, 아래=반박, 중심선=계보"가 설명 없이 읽힌다.
  - 100노드에서도 정보 과밀로 무너지지 않는다(또는 compact 폴백이 자연스럽다).
  - 색 없이 기호+텍스트만으로 상태 구분 가능(§9 접근성).
- **실패 시**: terminal-first를 재검토(웹 뷰어 조기 도입 등). 0a와 **병렬 진행 가능**(서로 의존 없음).

### 0c. 그래프 연산 + 상태 + Export 결합

- **전제**: 0a·0b 통과 후에만 착수. 부록 A(이벤트 로그 원본)·부록 B(상태 머신) 결정이 여기서 처음 코드화.
- **범위**: `fork`, `deepen`, `challenge`, `synthesize`, `close` 5연산 + 상태 전이 + 노드 상세 + 체크박스 Actions + Weekly preview + Markdown export.
- **성공 기준**: 원문 §18 시나리오 1~10을 단일 사용자·로컬에서 처음부터 끝까지 완주.
- **명시적 제외**(Phase 1+로 이월): 컬러·애니메이션, 다중 에이전트, saturation/dedup 감지, 실시간 동기화, presence/claim/lease.

### 검증 순서 요약

```text
0a Framing (단독)  ─┐
                    ├─(둘 다 통과)─▶  0c 결합  ─▶  Phase 1
0b TUI 레이아웃 ────┘
```

원문 §22의 "권장 검증 3종"을 **Phase 0의 사후 검증이 아니라 Phase 0 자체의 게이트**로 끌어올린 것이 핵심 변경이다.
