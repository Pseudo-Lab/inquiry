# ADR-D1 — Canonical 저장 형식

- 상태: **Accepted**
- 작성일: 2026-08-28
- 확정일: 2026-09-02
- 관련: PRODUCT-CONCEPT §4.7 §16 §21.2 · REVIEW 부록 A

## 맥락

원문 §16이 canonical source 후보 3안(이벤트 로그 / Markdown / 로컬 DB)을 병렬로 열어뒀다. 핵심 긴장은 **이식성(§4.7)** 대 **실시간 동기화·충돌 복구(§11)** 로, 두 요구가 반대 방향으로 당긴다. 이 결정은 거의 모든 하위 설계의 뿌리라 M0에서 확정해야 한다.

## 결정

**이벤트 로그를 canonical로 한다. Markdown은 projection, 로컬 DB는 파생 인덱스.**

- **원본:** `.inquiry/events.jsonl` (append-only). 모든 상태·그래프는 이벤트 재생으로 도출.
- **Markdown projection:** 엔티티 파일과 `outputs/`는 언제든 재생성 가능한 산출물(§4.7 이식성 흡수). 사람 편집은 import round-trip으로 사람 승인 후 이벤트화(§14, §21.9).
- **파생 인덱스:** 읽기 성능이 필요해지면 SQLite 등 캐시를 두되 **진실이 아님**(언제든 재생성). MVP(M2)에서는 메모리 재생만으로 충분.

## 근거

- §4.5(실패 아이디어 보존), §11(충돌→브랜치 보존), §16(누가·언제·무엇 감사)는 **전부 이벤트 로그가 있어야 성립** → 어느 안을 골라도 이벤트 로그는 사실상 필수.
- 세 안의 강점(동기화·감사 / 이식성 / 쿼리 성능)을 원본·projection·파생인덱스 3레이어로 분리해 각각 취득.

## 결과 · 트레이드오프

- **정직한 문구 조정 필요:** §4.7을 "원본은 개방형 이벤트 로그(JSONL) + 언제든 Markdown export"로 수정. "Markdown이 원본"이라는 인상을 주지 않는다.
- 상태 계산에 재생 비용 발생 → 그래프가 커지면 스냅샷/파생 인덱스 도입.
- 모든 상태 전이(D5)는 이 로그에 `{from, to, trigger, actor, at, reason?}`로 append(정합).

## 대안 (기각)

- **Markdown 원본:** 이식성 최고이나 실시간 병합·충돌 복구가 파일 병합 지옥.
- **로컬 DB 원본:** 쿼리 성능 최고이나 불투명 → §4.7 이식성 약속 위배.
