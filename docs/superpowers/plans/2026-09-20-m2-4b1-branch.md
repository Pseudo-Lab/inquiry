# M2-4B-1 Branch Implementation Plan

> **For agentic workers:** Apply test-driven-development and verification-before-completion task by task. 기존 승인된 M2 계획의 fork를 첫 독립 실행 단위로 구현한다. 커밋·푸시·실제 API 호출은 하지 않는다.

**Goal:** Framing으로 만든 가설 하나에서 AI 후보를 만들고, 사람이 선택한 후보만 자식 suggested 가설로 저장한다.

**Architecture:** 기존 Runner/Store를 재사용한다. BranchProposed는 RunSucceeded와, BranchAccepted는 자식 생성과 각각 하나의 이벤트로 저장한다. 요청 시점 부모 snapshot을 replay가 RunStarted에서 파생하고 승인 시 현재 부모와 비교한다. SDK에는 최소 문맥만 전달한다.

**Tech Stack:** Python 3.9+, 현재 `.venv`와 의존성, unittest. 새 라이브러리 없음.

## Global Constraints

- 정본: [M2 §6](2026-09-17-m2-implementation.md). fork: 부모 하나, 후보 2~4개, 승인된 후보만 suggested로 반영.
- deepen/challenge/AI synthesize는 후속 M2-4B 작업이다. 기존 수동 close/synthesize CLI는 유지한다. TUI 통합·상세 선택·Actions/export는 이번 범위가 아니다. Gate B 미검증 상태를 유지한다.
- 사용자 `.env`와 실제 `.inquiry` 데이터는 읽거나 변경하지 않는다. 테스트는 임시 디렉터리·fake adapter·MockTransport만 사용한다. 사용자 테스트 실행 보고를 계정 접근/모델 품질/Gate B 통과로 추정하지 않는다.
- 부모 상태는 suggested/exploring/supported/contested만 허용한다. suspended/refuted/human-closed는 기존 사람 명령과 재개 근거가 필요하다. synthesized는 현재 재개할 수 없으며 다른 허용 부모를 선택한다. Branch 자체는 부모 상태를 바꾸지 않는다.
- 실패·거절·취소·미승인은 그래프를 변경하지 않는다. 재시도/재생성은 새 명시 실행이다. API 성공은 가설 지지/반박 확정이나 Evidence 생성이 아니다.
- 기존 로그 형식을 보존한다. 새 필드는 projection에 기본값으로 추가하며 기존 RunStarted의 필수 필드나 schema_version을 바꾸지 않는다.

## 사용자 흐름과 대안

기존 번호형 대화 흐름을 이어 `chat`의 accepted 요약 아래 `1 Branch / 2 Save & Exit`를 둔다. Branch → 부모를 번호로 선택 → 명시 Generate → 후보 미리보기 → Accept Selected/Reject/Save & Exit 순서다. Accept Selected에서 `1,3`처럼 번호 목록 또는 `all`을 입력한다. 선택한 후보들이 한 번에 저장되며 선택하지 않은 후보도 제안 이력에는 남는다.

기존 상태 조회만 하던 accepted chat은 이제 위 메뉴를 제공한다. 단발 `show`와 `framing next`의 읽기 동작은 유지한다. ID를 복사하는 단발 명령만 추가하는 대안은 사용자가 보고한 부담을 해결하지 못하므로 주 사용 경로로 삼지 않는다. 다섯 연산을 동시에 구현하는 대신 먼저 Branch의 전체 승인 경계를 검증한다.

pending 제안은 같은 부모에 하나만 허용하고 다시 표시할 때 모델을 호출하지 않는다. 거부하면 이유와 후보를 남긴다. 다시 Branch/Generate를 선택하거나 단발 propose 명령을 실행해야 새 제안을 만든다. 채택된 제안에 추가 후보를 뒤늦게 붙이지 않는다.

## 데이터 계약

`inquiry/branch_schema.py`는 순수 모듈이다.

```python
validate_branch(payload) -> dict
parent_snapshot(hypothesis) -> dict  # JSON roundtrip of dataclasses.asdict
parent_context(snapshot) -> dict    # id,title,claim,parent_ids,status,assumptions,falsified_if only
BRANCH_SCHEMA: dict
BRANCH_PARENT_STATES = frozenset({'suggested', 'exploring', 'supported', 'contested'})
```

모델 출력은 정확히 `{"candidates": [...]}`이며 후보는 candidate_id/title/claim/difference의 네 nonblank 문자열이다. 2~4개, 후보 ID는 유일, 제목/주장은 공백·대소문자 정규화 후 정확한 중복을 거부한다. 의미상 새로움을 자동 판정하지 않는다. 부모 claim과 정확히 같은 후보 claim도 거부한다.

State 끝에 `branch_proposals: dict = {}`를 추가한다. 값은 아래 projection이다. 기존 Framing의 제안과 같은 detached dict 방식이며 외부 모델이 상태/ID 매핑을 정하지 않는다.

```python
{
  'id': 'P-...', 'run_id': 'R-...', 'parent_id': 'H-001',
  'parent_snapshot': {...}, 'candidates': [...], 'status': 'pending',
  'selected_ids': [], 'hypothesis_ids': {}, 'reason': None,
}
```

Run 끝에 `target_snapshot: Optional[dict] = None`을 추가한다. `hypothesis.fork` RunStarted를 replay할 때 정확히 하나의 부모 ID, session_id=None, 허용 상태를 확인하고 해당 시점의 부모 전체 snapshot을 파생한다. 이 값은 요청 context나 키에서 만들지 않는다. 기존 operation에는 None이다. RunStarted 변경은 단독 이벤트여야 해서 같은 줄에 부모 변경을 섞어 snapshot을 바꾸는 우회를 막는다.

| change kind | kind 외 필드 | 계약 |
|---|---|---|
| BranchProposed | proposal_id,run_id,parent_id,parent_snapshot,candidates | agent:runner, 정확히 RunSucceeded와 같은 묶음. 해당 Run의 operation/target/session/원본 출력과 일치. 시작 snapshot=제안 snapshot=현재 부모 snapshot. 기존 pending 없음 |
| BranchRejected | proposal_id,reason | human: 주체, pending만, 단독 변경 |
| BranchAccepted | proposal_id,selected_ids,hypothesis_ids | human: 주체, pending만, 현재 부모 snapshot 일치 및 허용 상태. 선택 1~4개, 중복/없는 ID 거부. 매핑은 선택과 정확히 같은 키, 새 고유 Hypothesis ID |

`BranchAccepted` 이벤트는 정확히 승인 변경 하나와 선택된 후보의 HypothesisCreated들이다. 후보 원래 순서로 저장하고 부모 `[parent_id]`, title/claim은 저장된 제안과 동일, assumptions/falsified_if=[]다. 그 외 변경·부분 묶음·추가 자식·주장 변조를 거부한다. 모든 자식은 suggested다.

저수준 중복 승인은 오류다. 서비스의 같은 제안+같은 선택 집합 재승인은 기존 매핑만 반환하고 쓰지 않는다(입력 순서 차이는 같은 선택). 다른 선택으로 재승인하면 거부한다. 부모가 나중에 바뀌어도 이미 완료된 같은 승인의 반환은 가능하다.

```python

```

- [x] RED: fake 생성 → 저장된 preview → 부분 승인 → restart, 부모/근거 불변, 자식 parent_ids와 suggested, 동일 선택 재승인 no-op을 실제 Store로 검사한다.

- [x] RED/GREEN: 저장 전/후 SystemExit, 중간 취소/잘못된 출력/예외, source 변경, known usage 보존, 명시 Runner.recover 후 새 실행을 검사한다. 제안 미리보기/승인 재개에는 모델을 다시 부르지 않는다.
