# M2-4B — Deepen · Challenge · Synthesize 설계안

상태: Challenge 저장 방식 확정, 구현 전 상세 설계. 2026-09-21 사용자가 A안(검토 메모)을 선택했다. 기존 M2 계획에 따라 세 연산을 순차적으로 구현하며 아직 구현 완료가 아니다. [상세 구현 계획](../plans/2026-09-21-m2-4b-remaining-operations.md)을 따른다.

## 범위와 공통 계약

기존 Branch와 같은 모델 제안 → 사람 승인 → 원자적 저장 흐름을 사용한다. 승인 전에는 가설·근거·상태를 바꾸지 않는다. 제안은 저장 후 재개할 수 있고, 승인·거부·조회는 SDK와 키 없이 가능해야 한다. 대상 가설이 제안 당시 스냅샷과 달라지면 승인을 거부한다. 중복 승인으로 중복 변경을 만들지 않는다.

기존 Run·사용량·취소·복구와 progress batching을 재사용한다. 잘못된 출력, 취소, 공급자 실패는 가설 변경을 남기지 않는다. 외부 자료를 자동 수집하지 않으며 전송 문맥과 비용 가능성을 호출 전에 알린다. 새 의존성, 실제 유료 API 검증, TUI 통합, Actions/export는 이번 범위에 없다. 사용자 파일과 키를 변경하거나 커밋·푸시하지 않는다.

## 1. Deepen

- 대상: suggested / exploring / supported / contested 가설 하나.
- 제안: 추가할 전제(assumptions), 반증 조건(falsified_if), 보완 이유. 각 항목은 검증된 사실이 아닌 검토 제안이다.
- 승인: 기존 ID·title·claim·부모·상태를 유지하고 전제/반증 조건을 중복 없이 추가한다. 기존 항목을 삭제하거나 AI가 원 주장을 덮어쓰지 않는다.
- 화면: 기존 항목과 추가 예정 항목을 구분하고 전체 승인 / 거부 / 저장 후 종료를 제공한다. 자유 편집과 항목별 부분 승인은 이번 범위에서 제외한다.
- 이력: 보완 이벤트로 변경 전후를 추적하고 기존 이벤트를 수정하지 않는다. 해당 가설에 대한 이전 미승인 제안은 스냅샷 불일치 시 stale로 처리한다.

## 2. Challenge — 검토 메모로 저장 (확정)

M2 정본은 반론 후보를 만들되 외부 Evidence나 refuted 판정으로 취급하지 말라고 규정한다. 사용자는 별도 검토 메모로 보관하는 A안을 선택했다.

### 선택한 방식

원 가설에 연결된 반론 문장·이유·확인할 조건을 제안하고 승인한 내용을 검토 메모로 보존한다. 가설 수와 원 가설 상태는 그대로다. 메모는 모델의 의견이며 독립 근거가 아님을 표시한다. 승인된 메모를 저장·조회하는 투영을 추가해야 하지만, 확인되지 않은 비평이 그래프를 계속 늘리는 일을 피할 수 있다.

### 채택하지 않은 대안

Branch처럼 2~4개 반론 후보 중 선택한 것을 suggested 가설로 저장한다. 기존 Branch의 후보 선택 흐름을 활용할 수 있고 반론에서 후속 탐구를 이어가기 쉽지만 가설 수가 늘어난다. 부모 연결은 계보일 뿐 Evidence의 challenges 관계가 아니며 원 가설의 상태는 바꾸지 않는다.

새 자식 가설 방식과 두 방식 동시 제공은 이번 구현에서 제외한다. 대상은 Deepen과 같은 활성 상태의 가설 하나다. 1~3개 반론(반론 문장·이유·확인할 조건)을 한 제안으로 제시하며 전체 승인 시 한 검토 메모로 보관한다. 부분 승인·메모 편집·삭제는 이번 범위에서 제외한다. 승인된 메모는 상태가 바뀐 뒤에도 읽을 수 있으며 새로운 생성의 입력으로 자동 재전송하지 않는다.

## 3. Synthesize

- 대상: 서로 다른 부모 2개 이상. ADR-D5에 따라 모든 부모가 supported 또는 contested여야 한다.
- 제안: 새 가설의 title·claim·전제·반증 조건과 통합 이유. 통합해도 해결되지 않은 차이는 숨기지 않는다.
- 승인: 새 suggested 가설 생성, 모든 부모 연결, 부모들의 synthesized 전환, 제안 승인 기록을 하나의 변경 묶음으로 저장한다. 기존 수동 synthesize의 원자성과 전이 검증을 유지한다.
- 부모 하나라도 없어지거나 상태/스냅샷이 바뀌면 전체 승인을 거부한다. 새 가설만 생성하거나 일부 부모만 전환하지 않는다.
- 새 가설의 탐색 시작은 별도 사람 명령이다. suggested 가설을 합치기 위해 상태를 자동 승격하지 않는다. 적격 부모가 없는 새 탐구에서는 통합이 불가능한 이유를 설명한다.

## 구현 순서와 검증 기준

Deepen → Challenge(검토 메모) → Synthesize 순서로 각각 테스트를 먼저 작성하고 저장·재생 계약, 서비스, 어댑터, CLI/chat을 연결한다. 기존 Branch를 전면 재작성하지 않는다. 메뉴는 Check 아래 Deepen/Challenge를 두며 Synthesize는 적격 부모가 2개 이상이거나 저장된 통합 제안이 있을 때 노출한다. 적격 부모가 없어져 stale이 된 제안도 조회·거부할 수 있어야 한다. 기존 Save & Exit 번호에 의존하는 테스트도 회귀 검증한다.

각 연산마다 제안만 저장된 상태, 승인·거부, 재시작, 중복 승인, stale, 잘못된 출력, 취소·중단, 알 수 없는 사용량을 검증한다. 원본 가설·근거의 무승인 변경을 거부하는 replay 테스트와 fake adapter의 실제 Store 통합 테스트를 포함한다. 전체 unittest, compileall, diff 검증과 독립 리뷰 후 완료를 보고한다. 실제 모델 품질 및 TUI Gate B는 별도다.

## 자체 검토

공통 승인 경계와 ADR-D5 통합 전이는 기존 계획과 일치한다. Deepen은 원 가설 보존을 추가 전용 보완으로 구체화했다. Challenge의 저장 형태는 사용자 결정으로 해소했다. 출력 개수·전체 승인·읽기 경로는 상세 구현 계획의 제한된 구현 선택이며 새 제품 기능을 추가하지 않는다. 최초 테스트 완료 보고는 기능별 성공이나 품질 통과로 확대하지 않았다.
