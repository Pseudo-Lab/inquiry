# M2 Gate B 사람 사용성 검증 — 프로토콜 & 기록

> 목적: [ADR-D7](../decisions/ADR-D7-staged-m2-gates.md)/[m2-entry-check](m2-entry-check.md)의 Gate B 4개 항목을 **사람 실측**으로 검증한다. 통과 전에는 M2-6 TUI 통합을 시작하지 않는다.
> 상태: 진행 중 (시작 2026-10-09).
> 정본 판정: 각 세션 결과를 이 문서에 기록하고, 통과/미통과 요약만 [m2-entry-check](m2-entry-check.md) Gate B에 반영한다.

## 공통 규율 (프로젝트 원칙)

- **기록 5종:** 실행 일시 · 입력(사용자가 실제로 친 것) · 관찰 · 문제 · 조치. 모든 세션에 남긴다.
- **코칭 금지:** 진행자는 질문을 **다시 풀어주거나 같은 질문을 반복하지 않는다.** 그렇게 했다면 그 자체를 **실패로 기록**한다.
- **참여자:** 기존 사용자(제작자)일 필요 없음. 가능하면 **처음 보는 사람**이 타당성이 높다. 제작자가 직접 할 경우 "제작자 자기검증"이라고 명시(편향 가능성 기록).
- **대체 금지:** 에이전트 시각 점수·자동 fixture 테스트로 사용성 판정을 **대체하지 않는다.**
- **해결 방식 제약(항목2):** 불편을 클릭/방향키 노드 탐색을 앞당기는 방식으로 해결하지 않는다 — 요약/페이지 방식을 고친다.

## 항목 1 — 최초 Framing UX  ⭐ 먼저 진행

**검증 질문:** 실제 사용자가 안내된 질문을 보고 **한 번의 탐구에서 3~5문항 안에** 중심 질문·쓰임·충분성을 구체화하는가?

### 준비
```bash
# 저장소 루트에서. 테스트 데이터는 repo 밖 깨끗한 폴더로 격리.
mkdir -p ~/inquiry-gateb-s1
cp .env ~/inquiry-gateb-s1/.env     # 키/모델 재사용 (출력·커밋 안 함)
```

### 실행 (참여자가 직접)
```bash
.venv/bin/python -m inquiry --dir ~/inquiry-gateb-s1 chat
```
- 참여자는 **자기 머릿속에 있는 진짜 질문**(막연해도 됨)으로 시작한다.
- 진행자는 화면만 보고 **아무 설명도 하지 않는다.**

### 관찰 체크리스트 (M1a exit 기준)
| # | 기준 | 관찰 | 판정 |
|---|---|---|---|
| 1 | 질문이 **유도적이지 않음** (특정 답을 떠먹이지 않음) | | ☐ |
| 2 | **3~5문항** 안에 프레임 수렴 (문항 수 기록) | | ☐ |
| 3 | 결과 프레임의 **중심 질문·쓰임(use)·충분성 기준**이 참여자 의도와 맞음 | | ☐ |
| 4 | 참여자가 **진행자 개입 없이** 완료 | | ☐ |
| 5 | (재개 경로) 중단 후 재개 시 **기존 답변 재수집 불필요** | | ☐ |

### 실패 신호 (하나라도 있으면 기록)
- 진행자가 질문을 다시 풀어줌 / 같은 질문 반복 / 참여자가 "무슨 뜻이냐" 되물음
- 6문항 넘어가도 프레임이 안 잡힘
- 프레임이 참여자가 하려던 것과 어긋남

### 📝 세션 1 기록 (완료)
- 실행 일시: 2026-10-10 (02:55~03:13 UTC, events.jsonl 기준)
- 참여자: **제작자 자기검증** — ⚠️ 편향 가능성: 설계 의도·질문 흐름을 이미 알고 있어 "처음 보는 사람"보다 막힘이 과소평가될 수 있음. 통과해도 외부인 검증 1회가 남는다고 본다.
- 테스트 폴더: `~/inquiry-gateb-s1` (깨끗 — 사전 기록 0). 세션 `F-213ee7fa…`.
- 입력 seed: "직무와 스킬을 계층 구조를 갖는 그래프로 만들고싶어. HR 도메인에서 전체 직무와 해당 직무와 연관된 하드 스킬을 구조화하려면 어떤 방법들을 사용해볼수있을까"
- **문항 수: 5** (3 기본 + 2 적응형 후속)
  1. 이 그래프로 무엇을 가장 알고 싶거나 바꾸고 싶나요?
  2. 만든 직무·스킬 구조를 어떤 결정이나 산출물에 쓰려 하나요?
  3. 어떤 상태가 되면 이 구조화가 충분하다고 느끼겠나요?
  4. 처음에는 어떤 국가·언어권과 직무 범위부터 담고 싶나요? (적응형)
  5. 우선 활용할 내부 데이터나 외부 표준 분류체계가 있나요? (적응형)
- 세션 흐름: 5문항 답변 → 프레임 제안(P-de2c54…) → **reject** (사유 명시) → 재생성(P-9593297…) → **수락**. branch 1회까지 진행.
- **reject 사유 (기록됨, seq 34):** `"4번은 없애고싶어"` — 가설 **H4를 제거하라는 명시적 지시** (사용자 확인 2026-10-10).

#### ① 객관 지표
| 지표 | 값 | 합격선 | 판정 |
|---|---|---|---|
| 문항 수 | 5 | 3~5 | ✅ |
| 진행자 개입(코칭) | 0 | 0 | ✅ |
| 참여자 되물음 | 0 (기록상 없음) | ≤1 | ✅ |
| 프레임 생성 완료 | Y (수락) | Y | ✅ |

#### ② 앵커 사다리 (L0~L4)
| 축 | 등급 | 근거 |
|---|---|---|
| 질문 비유도성 | **L4** | 전 질문 개방형·명료화 목적. 특정 답 유도 없음. 적응형 질문도 범위(국가/데이터)만 좁힘 |

#### ③ 가설 상호 차별성 (참고)
H1 표준 탑다운 / H2 내부데이터 보텀업 / H3 하이브리드 온톨로지+근거관리 / H4 추천과업 우선 — 4개가 **서로 다른 설계 접근**으로 명확히 차별화(중복 아님).

- **관찰:** 되물음·코칭 없이 5문항에 수렴하는 **대화 흐름 자체는 양호**. 그러나 **거부→재생성 루프가 사용자의 명시적 지시를 지키지 못함** (아래 결함 1). 수락된 최종 프레임에 출력 결함도 1건(아래 결함 2).

- **🔴 결함 1 — reject 지시 미반영 (기능 결함) → ✅ 수정·검증 완료 (2026-10-10):** 사용자가 `"4번은 없애고싶어"`로 **가설 H4 제거**를 지시했으나, 재생성된 프레임(수락본)에 H4가 **그대로 생존**했었다.
  - 첫 제안 H4: "추천 목적 역설계형 그래프 모델" → 재생성 H4: "추천 과업 우선의 다층 그래프 설계". **제목만 바뀌고 4번째 가설이 유지됨.**
  - **근본 원인 (코드):** 재생성이 거부 사유를 모델에 전달하지 않는 블라인드 re-roll이었다 — 3겹. ① `framing_state.py`가 reject 시 `reason`을 세션 proposal에 보존 안 함. ② `framing.py`의 재생성 요청 context가 `seed`·`qa`만 담음(거부 제안·사유 없음). ③ `openai_adapter.py` framing payload가 `seed`·`qa`만 전송. ④ `framing_prompts.py` FRAMER_SYSTEM이 "seed와 qa만 근거로"라 피드백 반영 지시 자체가 없음.
  - **수정:** 네 지점 모두 거부 프레임+사유를 흘려보내도록 변경 + FRAMER_SYSTEM에 "rejected 사유를 반드시 반영(예: 특정 가설 제거 요청이면 다시 제시 않고 대체)" 지시 추가. 회귀 테스트 2건 추가([test_framing_flow](../../tests/test_framing_flow.py) `test_regeneration_forwards_rejected_frame_and_reason`, [test_openai_adapter](../../tests/test_openai_adapter.py) `test_rejected_feedback_is_included_in_framing_payload`). 전체 **279개 통과**.
  - **실 API 재검증:** 같은 HR Taxonomy 시나리오로 첫 제안 H4("표준 분류 기반 코어와 한국형 확장 그래프")를 `--reason "4번 H4 … 없애고 싶어"`로 거부→재생성 → **H4가 "직무 전이 경로 중심 그래프"로 대체되고 거부 가설은 사라짐**(H1~H3 유지). 지시가 반영됨.

- **🟠 결함 2 — 플레이스홀더 누수 (출력 품질) → ✅ 수정·검증 완료 (2026-10-10):** 수락된 프레임의 `scope.exclude[3]`가 `"미정 — 후속 확인 필요"`로 채워졌었다. 원인은 FRAMER_SYSTEM의 "근거가 부족한 항목은 '미정 — 후속 확인 필요'로 남긴다" 지시가 exclude에까지 광범위 적용된 것.
  - **수정:** FRAMER_SYSTEM에서 해당 플레이스홀더를 **open_questions 전용으로 한정**하고, scope(include/exclude)는 실제 내용만 담되 **빈 자리를 플레이스홀더로 패딩하지 말고 제외할 것이 없으면 비우라**고 명시. (`scope.exclude`는 스키마상 minItems=0이라 빈 배열 허용.)
  - **실 API 재검증:** 새 세션에서 프레임 생성 시 `exclude: []`로 정상 출력, scope에 플레이스홀더 누수 없음. 전체 **279개 테스트 통과**.

- **❌ 이전 기록 오류 정정:** 직전 버전에서 "첫 제안 reject 사유가 없어 사후 재구성 불가"라고 적었으나 **오류**였다. 사유는 `FrameRejected` 이벤트(seq 34)에 `reason: "4번은 없애고싶어"`로 **정상 저장**돼 있었다. (검토 시 이벤트 내부 필드를 열지 않고 집계만 한 데서 비롯.)

- **판정: 🟡 자기검증 통과 — 결함1·2 수정완료, 외부인 검증만 잔여.** M1a 대화 기준(유도성 L4·5문항 수렴·의도정합·무개입) 충족. 발견한 **결함 1(거부→재생성 미반영)·결함 2(플레이스홀더 누수) 모두 수정·실API 재검증 완료**. 남은 블로커: **외부인 검증 1회**(제작자 편향 보정) 뿐. 그 전까지 Gate B 항목1 **최종 통과로 올리지 않는다.**

## 항목 2 — 100노드 탐색

**검증 질문:** 선택한 Git-log 화면과 기본 CLI 도움말로, 지정한 가설의 **부모·합류 입력 2개·종료 이유**를 설명 개입 없이 찾는가? 누락 노드·틀린 연결 없이, 페이지 이동 부담은?

### 실행 (참여자가 직접)
```bash
# 100노드 × 120열, 페이지별 탐색. 전체를 페이지로 나눠 보여줌.
python3 prototypes/m1b-layout/scale.py --nodes 100 --width 120 --page 1
python3 prototypes/m1b-layout/scale.py --nodes 100 --width 120 --page 2   # ... 이하 페이지
```

### 과제 (진행자가 지정, 설명은 금지)
1. 특정 가설 ID 하나를 지목 → 그 **부모**를 찾아라.
2. 합류(merge)된 가설의 **입력 2개**를 찾아라.
3. 종료된 가설의 **종료 이유**를 찾아라.
